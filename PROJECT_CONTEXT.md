# Контекст проекта techaudit

Актуализировано: 30 октября 2026 года. Документ составлен по текущим исходникам, структуре каталогов и README. Используйте его как стартовый контекст для следующих задач; при изменении поведения обновляйте соответствующие разделы.

## 1. Назначение и архитектура

Это локальный Python-инструмент технического SEO-аудита сайтов нескольких торговых сетей. Он собирает HTML и результаты HTTP-проб с production-сайтов, сравнивает версии страницы для разных User-Agent и после JavaScript, выполняет проверки чек-листа, формирует HTML/XLSX-отчёты и показывает историю в веб-интерфейсе.

Дополнительные сценарии: импорт краулов Screaming Frog, сравнение страниц из поисковых источников с краулом для поиска сирот, внешние проверки PageSpeed/GSC, ИИ-сводки, подготовка ТЗ и чат по ТЗ.

Архитектура — одно Python-приложение с консольными точками входа и серверным веб-интерфейсом. Общие данные лежат в SQLite и файловом каталоге `data/`. Отдельной сборки frontend нет: сервер отдаёт Jinja2-шаблоны, CSS и JavaScript.

Технологии: FastAPI, Uvicorn, Jinja2, HTMX, Chart.js; httpx и requests; Playwright/Chromium; lxml; openpyxl; python-dotenv; google-auth. Зависимости перечислены в `requirements.txt` с нижними ограничениями версий либо без фиксации. Синтаксис исходников требует Python 3.10+; отдельная точная версия Python в requirements не закреплена.

## 3. Основной поток данных

1. `config.load_settings()` загружает окружение и настройки, сохранённые через интерфейс.
2. `db_registry.entries_for()` получает список страниц из БД; если для сети записей нет, используется CSV из `registry/`.
3. `collect_html.py` → `techaudit.collect.main()` собирает варианты страниц, пробы и ресурсы, сохраняет результаты через `Store`.
4. `diff.py` и `comparer.py` сравнивают сохранённые варианты, `diffreport.py` создаёт HTML-отчёт.
5. `run_checks.py` → `checks.cli.main()` выполняет проверки по запуску; дополнительные сетевые этапы включаются флагами `--live`, `--external`, `--ai`.
6. Результаты попадают в `check_results`; отчёты строятся из сохранённых данных, веб-метрики агрегируются из тех же таблиц.
7. Веб-задания используют те же консольные сценарии через `web/jobs.py`, а не отдельную реализацию аудита.

Варианты страницы:

| Вариант | Источник |
|---|---|
| `plain` | сырой HTTP-ответ, обычный User-Agent |
| `bot` | сырой HTTP-ответ, User-Agent поисковика |
| `browser` | DOM после JavaScript в Chromium, User-Agent поисковика |
| `browser-plain` | DOM после JavaScript, обычный User-Agent |

Обычная выборка: `plain,bot,browser`; стандартные пары сравнения: `plain:bot,bot:browser`. Блоки HTML сопоставляются по стабильным маркерам (`data-qa`, `data-testid`, `id`, семантические теги, role/itemtype), числовые части нормализуются.

## 5. Проверки и отчёты

В `techaudit/checks/`:

- `core.py`: `Item`, `Result`, `CheckDef`, `CheckSettings`, `PageDoc`, реестр `REGISTRY`, декоратор `@check`, роли страниц и правила noindex.
- `ctx.py`: контекст `Ctx`, доступ к данным запуска, схема результатов и живых выборок.
- `runner.py`: регистрация, выполнение и сохранение результатов. `--only` заменяет результаты только выбранных проверок.
- `c_http.py`, `c_markup.py`, `c_render.py`, `c_seo.py`: основные проверки HTTP, разметки, рендеринга и SEO.
- `c_crawl.py`, `c_external.py`: проверки на данных краула и внешних сервисов.
- `x_meta.py`, `x_robots.py`, `x_server.py`, `x_urls.py`: дополнительные проверки.
- `extras.py`: метаданные дополнительных пунктов, добавление их в отчёт.
- `live.py`: дополнительные запросы к production для живой выборки.
- `checklist.py`: загрузка и сопоставление строк Excel-чек-листа.
- `report.py`: генерация отчётов; `plan.py`: план работ, роли и трудозатраты.
- `ai_stage.py`: ИИ-анализ результатов; `cli.py`: общий сценарий запуска проверок.

Статусы: `pass` — пройдено, `fail` — не пройдено, `warn` — требует внимания, `skipped` — пропущено, `na` — нет данных. Не объединять эти состояния. Исключение внутри отдельной проверки сейчас перехватывается runner и превращается в `skipped` с описанием ошибки.

Строки исходного Excel сопоставляются с проверками по подстрокам названия, а не по номеру строки. Исходный файл не изменяется: создаётся копия с результатами. Путь задаётся через `--checklist`, `CHECKLIST_XLSX` либо поиск подходящего файла рядом с проектом.

Важно: `runner.load_all()` импортирует `c_crawl` и `c_external` после остальных модулей и вызывает `c_crawl.install()`. Этот порядок влияет на замещение ранее зарегистрированных проверок.

## 6. Веб-интерфейс

`techaudit/web/app.py` содержит `create_app(env_file=None, start_jobs=True, extra_hosts=())`, маршруты и связующую логику. Приложение создаёт схемы БД, при пустом справочнике загружает начальные файлы, подключает шаблоны, статику и отчёты. Менеджер заданий запускается и останавливается через lifespan.

Группы маршрутов: `/` и `/api/*` — обзор и графики; `/explore`, `/block` — анализ блока; `/block/ai`, `/block/tz`, `/block/chat` — ИИ и ТЗ; `/checks` — проверки и доказательства; `/export/*` — выгрузки; `/crawl` — краулы; `/orphans` — сироты; `/ai` — ИИ; `/registry` и `/reference` — справочники; `/runs`, `/jobs`, `/schedules` — запуски и расписание; `/history` — история; `/settings` — доступ и настройки. Точный набор параметров смотреть в коде маршрута.

Шаблоны страниц называются по разделам (`checks.html`, `settings.html`, `block.html` и др.); файлы с `_` — частичные HTML-ответы, включая `_check_detail.html`, `_evidence.html`, `_block_tz.html`, `_block_chat.html`. Общая оболочка — `base.html`. Поведение и оформление находятся в `static/app.js` и `static/app.css`.

`jobs.py` хранит задания и расписания в БД, строит команды запуска, управляет очередью и логами. Расписание работает только при работающем веб-приложении, время расписания — локальное время машины.

## 7. Хранилище и источники правды

База по умолчанию: `data/techaudit.db`. Схемы распределены по модулям; общая точка создания — `webdb.init_all()`. Используется встроенный sqlite3, без ORM. Веб-подключение включает WAL, busy timeout и autocommit; явные транзакции оформляются через `webdb.tx()`.

| Таблицы | Содержимое / модуль |
|---|---|
| `runs`, `pages`, `diffs`, `probes` | сбор и сравнение, `storage.py` |
| `live_urls`, `check_results` | живые выборки и результаты, `checks/ctx.py` |
| `ref_sites`, `ref_page_types`, `ref_urls`, `ref_owners`, `ref_changes` | справочники и журнал, `db_registry.py` |
| `app_settings`, `app_networks` | настройки и секреты, `appsettings.py` |
| `web_jobs`, `web_schedules` | задания и расписания, `web/jobs.py` |
| `crawl_imports`, `crawl_pages` | краулы, `crawl.py` |
| `index_imports`, `index_pages`, `orphan_probe` | поисковые выгрузки и пробы, `indexed.py` |
| `orphan_runs`, `orphan_rows` | сравнение сирот, `orphans.py` |
| `ext_cache` | кеш внешних сервисов, `external.py` |
| `ai_cache`, `ai_notes` | кеш и заметки ИИ, `ai.py` |
| `run_debug` | сохранённые условия проверок, `webdb.py` |

БД — основной источник справочника; `registry/<сеть>.csv` пересоздаётся как зеркало. При первоначальном наполнении используются `справочники/*.csv` и CSV сетей. В текущей копии представлены CSV `5ka`, `chizhik`, `perekrestok`; фактический список настроенных сетей определяется конфигурацией, а не наличием файла.

Файлы страниц: `data/html/<run_id>/<сеть>/<тип>/<slug>.<вариант>.html`; тела проб — в `_probes/` внутри каталога сети. Сырые ответы сохраняются без вводного комментария, что важно для проверки charset в первых 1024 байтах. DOM браузерных вариантов содержит служебный комментарий источника и времени.

Метрики вычисляются по сохранённым результатам, а не ведутся как независимые снимки. Сравнение запусков зависит от одинаковости выборок, лимитов и вариантов страниц.

## 8. Настройки и ограничения

- Общая точка чтения настроек — `config.load_settings()`. Значения БД подставляются через `appsettings.py` поверх `.env` и переменных процесса. Если в БД заведены сети, список сетей берётся из БД.
- Поиск `.env`: явный `--env-file` → `TECHAUDIT_ENV` → файл уровнем выше проекта → файл в проекте. Файл служит запасным источником для незаданных в интерфейсе значений.
- Проверяется production. По умолчанию нужен токен сети; отправка без него включается явно диагностическим режимом. Доступ разрешается общим механизмом, не следует добавлять независимую загрузку токена в отдельный модуль.
- Токен передаётся только хостам соответствующей сети. Сохранять токены в результатах, доказательствах или логах нельзя. При этом секреты настроек действительно хранятся в БД: не считать её безопасной для публикации.
- `.gitignore` исключает `.env`, `service_accaunt/`, `data/`, `.venv/`, кеши Python и файлы ключей.
- Внешние сервисы опциональны; отсутствие ключей не должно прерывать весь аудит. PageSpeed/GSC используют кеш и несколько ключей/ресурсов.
- GSC-выгрузка страниц с показами — неполный индикатор наличия страниц в поиске, а не полный список индекса Google.
- Screaming Frog запускается отдельно: приложение импортирует готовый CSV, само полный краул Screaming Frog не выполняет.
- ИИ формирует сводки и черновики, не изменяет статусы проверок. Данные для модели готовятся в соответствующих сценариях; при изменениях отдельно проверять состав передаваемых фрагментов и истории чата.
- Сервер по умолчанию слушает `127.0.0.1:8765`, авторизации пользователей нет. В `app.py` есть проверка Host/Origin для защиты локального интерфейса; удалённый запуск требует явного `--allow-remote`.

## 9. Запуск и проверка изменений

Команды выполняются из корня проекта в подготовленном окружении:

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m playwright install chromium
python web.py --no-open
```

Основные сценарии:

```powershell
python collect_html.py --dry-run
python collect_html.py --network 5ka --limit 2 --probes all
python compare_html.py --run <run_id>
python run_checks.py --run <run_id>
python run_checks.py --live
python run_checks.py --external
python run_checks.py --ai
python import_crawl.py --network 5ka <crawl.csv>
python find_orphans.py --help
```

`--dry-run` показывает план без запросов к сайтам. Обычный сбор, `--live`, внешние API и ИИ имеют реальные сетевые эффекты; их не использовать как автоматическую проверку документации. Пересчёт сохранённых результатов может изменять БД и отчёты.

Тесты организованы преимущественно через `unittest`; в комментариях отдельных файлов также предлагается pytest. `pytest` не перечислен в `requirements.txt`.

```powershell
python -m unittest tests.test_checks tests.test_smoke
python -m unittest discover -s tests -v
```

| Тестовый файл | Область |
|---|---|
| `test_checks.py`, `test_checks_extra.py` | основные/дополнительные проверки и план |
| `test_smoke.py`, `mock_site.py` | сбор, доступ, пробы, сравнение на локальном mock-сайте |
| `test_web.py`, `test_web2.py` | справочники, импорт, метрики, задания, краулы, экспорт |
| `test_settings_ui.py` | сохранение настроек, окружение, секреты и sitemap |
| `test_dashboard_v3.py` | обзор блоков, страницы блоков, выгрузки |
| `test_noindex_flags.py` | noindex/nofollow в справочнике и проверках |
| `test_orphans.py` | импорт поисковых списков, сравнение, интерфейс сирот |
| `test_tz_chat.py` | история ТЗ-чата, разбор ответов, маршруты с подменённым ИИ |

Часть smoke-тестов использует Playwright и требует доступного Chromium. Наличие `.pytest_cache` не подтверждает успешность текущего набора тестов. При подготовке этого документа приложение, сбор и тесты не запускались: изучались исходники и структура файлов.
